description: Process a specific list of GitHub issue numbers, each in its own isolated worktree, by delegating to the handle-issues Workflow. Meant to run unattended/in the background.
argument-hint: "<issue-numbers> — one or more issue numbers, e.g. \"23 45 67\" (required — this no longer scans the backlog for you)"
---

You are the batch orchestrator for a specific list of GitHub issue numbers. You do **not** do implementation work yourself — every issue's claim/branch-link/plan/code/test/review/PR work happens inside `.claude/workflows/handle-issues.js`, invoked once per issue via the `Workflow` tool. Do not duplicate that logic here.

**Setup.**
1. Parse `$ARGUMENTS` as a whitespace/comma-separated list of issue numbers. If it's empty or contains anything that isn't a positive integer, stop and ask the user for explicit issue numbers — do NOT fall back to scanning the open-issue backlog for "oldest unclaimed" or anything similar. Issue numbers are always provided by the caller now.
2. Read `.claude/state/handle-issues-runs.json` if it exists (treat as `{}` if not — this file is gitignored, ephemeral orchestration bookkeeping, separate from the committed `.pipeline/*.md` audit-trail artifacts).
3. PROCESSED = [] (issue number, title, PR URL, verdict, or failure status — filled in as you go).

**Terminal statuses**: `shipped`, `abandoned`. **Resumable**: any `*-failed` status, `blocked-on-question`.

**Loop — for each issue number, in the order given, one at a time (not in parallel — this avoids two orchestrators touching the same repo state concurrently):**
1. `EnterWorktree` to get a fresh, isolated worktree for this issue. Each issue gets its own worktree, opened right before its run and closed right after — issues are never processed in a worktree left over from a previous issue in this same loop.
2. Look up this issue number's entry in the state file read in Setup. If it exists and its `status` is resumable (not terminal), use its `runId` as `resumeFromRunId`; otherwise this is a fresh run (no `resumeFromRunId`).
3. Invoke `Workflow({scriptPath: '.claude/workflows/handle-issues.js', resumeFromRunId, args: {issueNumber: <N>, worktreePath: <absolute path of the worktree just entered in step 1>, humanAnswer: <entry's pendingHumanAnswer, if any>}})` — use `scriptPath` (not `name`) on every call in this loop, including the first: repeated `Workflow({name:...})` calls in one session can silently reuse a stale script snapshot from an earlier call, `scriptPath` forces a fresh read every time. `worktreePath` is required — the script pins every one of its agent calls to that exact directory (see AGENTS.md's "Orchestration working-directory contract"); omitting it reintroduces the #41/#42 cwd-drift bug. The workflow itself claims the issue and creates/links its branch as its very first action, before any planning.
4. Sanity-check the result: confirm the returned `issue.number` matches the `<N>` you requested (a silent mismatch is the signature of the stale-snapshot bug above — if it doesn't match, stop and report this explicitly rather than continuing the loop).
5. Check whether this call failed due to a session/usage limit rather than a real pipeline problem: look at the Workflow tool result's own diagnostics (the `<failures>` block, if present) for text matching `session limit`, `usage limit`, or `resets? (at|on) ...`. Set `isRateLimited` accordingly — this determines how steps 6 and 8 below treat the result.
6. Take the `runId` from this Workflow call's own tool-result envelope (distinct from the script's returned `status`/`issue`/etc.) and write/update this issue's entry in `.claude/state/handle-issues-runs.json`: `{runId, status, phaseReached: status, updatedAt: <now>, attempts: (prior attempts ?? 0) + (isRateLimited ? 0 : 1), pendingHumanAnswer: null, prUrl, verdict, history: [...(prior history ?? []), {attempt: <the attempts value just computed>, status, reason: (isRateLimited ? '<matched rate-limit text>' : (result.reason ?? null)), at: <now>}]}`. Rate-limit hits do not consume an attempt and do not need their own history entry to look like a pipeline failure — they're recorded with their own `reason` text so the history stays honest about why a retry happened.
7. If `status` is `blocked-on-question`: do NOT just park it and move to the next issue. A workflow run cannot pause mid-flight and wait for you — `agent()` calls inside it run to completion and return structured JSON, there's no interactive primitive available to a subagent. So the moment control returns here, immediately surface the open question with `AskUserQuestion`, using `result.summary` for the question text and the planner's own proposed resolution(s) as one of the answer options (plus room for the user to give a different answer). Once answered, set `pendingHumanAnswer` on this issue's state entry and go back to step 3 in the SAME still-open worktree for this issue (do not `ExitWorktree` first) — this time `resumeFromRunId` is set, so the already-completed Setup+Plan phases replay from cache instead of re-running the planner. If it comes back `blocked-on-question` again (a second, different open question), repeat this step — ask again, don't give up after one round.
8. If `isRateLimited` (from step 5): this is not a pipeline failure, so don't apply the `attempts >= 3` rule below at all — track a separate `rateLimitRetries` counter (not persisted in the committed attempt count) capped at 2, so a bug in the detection regex can't cause an infinite silent-reschedule loop. Parse a reset time out of the matched text if one is present:
   - If the reset is within roughly 30 minutes, do a bounded wait (a backgrounded Bash until-loop polling `date` against the parsed time, or `sleep` in short increments) before going back to step 3 with `resumeFromRunId` set.
   - If it's further out (hours), use the `schedule` skill to create a one-shot scheduled resumption of this same command for this issue at the parsed reset time, then end this issue's processing cleanly for now (note in PROCESSED that it's scheduled to resume, with the time) rather than blocking the session.
   - If `rateLimitRetries` would exceed 2, stop treating it as rate-limited and fall through to step 9's normal failure handling instead (something else is likely wrong).
9. If `status` ends in `-failed` (and step 8 didn't already handle it as a rate limit): check `attempts` on this issue's state entry. If `attempts >= 3`, set `status: 'abandoned'` in the state file (terminal), stop retrying this issue, and note the failure in PROCESSED. Otherwise go back to step 3 to retry with `resumeFromRunId` set — only the failed phase and anything after it actually re-runs, the rest replays from cache.
10. Only move on from steps 7/8/9 once this issue reaches a terminal status (`shipped` or `abandoned`) — a scheduled-for-later rate-limit resumption (step 8) counts as "moved on" for this loop iteration too, since a separate scheduled invocation will pick it up.
11. `ExitWorktree` to close out this issue's isolated worktree before moving to the next one.
12. Append the issue number/title/PR URL/verdict/status to PROCESSED — including whether a human answer was needed and what it was, whether it was abandoned after repeated failures, and whether it was scheduled to resume later due to a rate limit.
13. Before moving to the next issue, judge honestly: has this conversation grown long enough that you're leaning on auto-compaction, or would another full pipeline risk degraded output? If so, stop early and say so in the final report — don't push through the remaining issue numbers. (The state file means a later invocation of this same command can pick up exactly where you left off, so stopping early costs nothing.)

**Final report.** Summarize:
- Every issue number requested, whether it was processed, and its outcome (PR URL + verdict, or the failure/blocked/abandoned status returned by the workflow).
- Any issue numbers not reached because you stopped early for context-safety reasons — note that re-running this command will resume them via the state file rather than starting over.

Never merge PRs, close issues, or push to `main` — the workflow and the repo's `.claude/settings.json` permissions/hooks already enforce this; do not attempt to work around them.

To run this fully unattended, invoke it as a backgrounded agent rather than in the foreground session, so it doesn't block your terminal while it works through the list.
